# 2026-09-04 5,000 Repository Result Analysis

## Executive Summary

The refined 5,000-repository run produced two plausible RFC candidates:

1. `http-cancellation`
2. `http-async-operation`

Cancellation is now the cleaner first candidate: it scores 69 in the base model
and 67 in strict mode. The strongest argument is convergence rather than
narrowness: 330 strict cancellation families use the dominant
`POST /.../{id}/cancel` shape. That is easier to pitch as codifying existing
practice than as proposing a new HTTP API shape.

The standardization gap is semantic. The corpus already shows the cancel
affordance. What remains underspecified is how an API advertises cancelability,
which response means “accepted but not complete”, which response means “too late
to cancel”, how clients observe the terminal state, and how cancellation
interacts with retries.

Async operation remains broad and important, scoring 68 in the base model and 67
in strict mode, but its strict family count is much lower after broad
`GET job/task/run` evidence is removed.

## Corpus Health

- Repositories processed: 5,000
- Independent implementation families: 4,993
- Repositories with detected evidence: 685
- Repositories with no detected evidence: 4,315
- Raw evidence records: 24,914
- Deduplicated evidence records: 14,004
- Extraction errors: 0

The run was operationally healthy: the pipeline completed on the external SSD,
used parallel streaming collection, and produced no final extraction errors. The
main measurement caveat remains corpus yield: 13.7% of the discovered
repositories contained routes that the deterministic extractors could classify.

Repository-level deduplication reduced evidence volume by 43.8% while retaining
separate `openapi` and `source` evidence for the same route shape.

## Candidate 1: HTTP Cancellation

### Why It Is Strong

- Shape convergence is high: 330 strict cancellation families use
  `POST /.../{id}/cancel`.
- This is a de facto practice argument, not a request to invent a new endpoint
  style.
- Explicit cancellation actions appear in 407 independent families after
  excluding the weakest `DELETE job/task resource` heuristic.
- The full detector found cancellation evidence in 463 independent families.
- The dominant shape is `POST /.../{id}/cancel`, but the corpus also shows
  `PUT /.../stop`, `PATCH /.../terminate`, `GET /.../cancel` signed/action
  links, and `DELETE` cancellation variants.
- The concept has low evidence concentration: the top repository contributes
  3.56% of deduplicated cancellation evidence.
- Strict evidence covers 87.9% of cancellation families, so the candidate is not
  mostly dependent on broad heuristics.

### Measured Shape Memberships

The table counts pattern-family memberships, not mutually exclusive family
partitions. A family can contribute more than one pattern.

| Pattern | Family memberships |
| --- | ---: |
| `post-subresource-cancel` | 330 |
| `post-action-cancel` | 106 |
| `delete-action-cancel` | 31 |
| `put-action-cancel` | 27 |
| `get-cancel-link` | 18 |
| `patch-state-cancelled` | 5 |
| `delete-operation-resource` | 209 |

`delete-operation-resource` is intentionally excluded from strict scoring unless
the path, operation name, or operation summary has explicit cancellation
wording.

### Async Overlap Risk

The async overlap is useful but double-edged. 89.8% of cancellation families
also have async-operation evidence. That supports composability, but it also
supports the opposing interpretation that cancellation is merely an affordance
of operation resources rather than an independent concept.

The cancellation-first path therefore has two viable framings:

1. a standalone cancellation profile that defines only minimal operation-handle
   vocabulary;
2. a cancellation section inside a broader operation-resource draft.

The first draft should explicitly answer why it is not standardizing the whole
async-operation model: the data show stronger convergence on cancel affordance
semantics than on the broader operation-resource shape.

### RFC-Shaped Core

The strongest proposal is not “standardize every cancel endpoint”. It is a
small HTTP interaction profile for cancelling long-running operations:

- how an operation advertises cancelability;
- how a client requests cancellation;
- what response status means “accepted, not complete”;
- what response status means “already completed, cannot cancel”;
- how clients observe terminal states after cancellation;
- how cancellation interacts with idempotency and retries.

## Candidate 2: HTTP Async Operation

### Why It Is Still Interesting

- The full detector found async-operation evidence in 631 independent families.
- The strict subset using `202 Accepted` mutations or explicit status resources
  still covers 239 independent families.
- Observed interaction patterns include `POST 202`, `POST job/run`,
  `GET status/progress/result`, generic operation resources, and non-POST
  mutations returning `202`.

### Why It Needs More Filtering

- Strict evidence covers 37.9% of async families, so broad `job` / `task` /
  `run` route naming still drives much of the base score.
- Deduplicated async evidence is still more concentrated than cancellation: the
  top repository contributes 16.74% of async evidence.
- Generated Kubernetes/OpenAPI catalogs still appear in the top contributors,
  even after repository-level deduplication.
- Generic `GET /jobs`, `GET /tasks`, and `POST /tasks` can describe ordinary
  resources rather than long-running operations.

### Measured Shapes

| Pattern | Families |
| --- | ---: |
| `post-job-resource` | 510 |
| `get-operation-resource` | 518 |
| `get-status-resource` | 156 |
| `post-202-accepted` | 133 |
| `mutation-202-accepted` | 29 |

### RFC-Shaped Core

The useful RFC target is a narrow operation-resource profile, not a broad
definition of asynchronous HTTP:

- creation request returns `202 Accepted` or a typed operation representation;
- operation resource has stable `status`, `progress`, `result`, and `error`
  fields;
- response links identify status, result, cancellation, and retry affordances;
- terminal states are explicit and reusable across APIs;
- idempotent retries are specified for operation creation.

## Prior Art and Standards Gap

The prior-art comparison is maintained in
`docs/prior-art/http-cancellation.md`.

Key takeaways from the 2026-09-04 check:

- [RFC 7240](https://www.rfc-editor.org/info/rfc7240/) defines `Prefer:
  respond-async` and gives a `202 Accepted` async response example, but leaves
  the later result process implementation-specific.
- [OData v4.0](https://docs.oasis-open.org/odata/odata/v4.0/os/part1-protocol/odata-v4.0-os-part1-protocol.html#_Toc372793755)
  defines status monitors and `DELETE` cancellation, including `202` for
  asynchronous cancellation.
- [Google long-running operations](https://developers.google.com/optimization/service/reference/rpc/google.longrunning)
  define best-effort cancellation and later observation through the operation
  resource, with successful cancellation represented as a terminal error state.
- [Azure guidance](https://github.com/microsoft/api-guidelines/blob/vNext/azure/Guidelines.md#long-running-operations--jobs)
  is strong on operation-location, polling, retry guidance, and repeatability,
  while public cancellation semantics vary by guideline or service.
- [RFC 9457](https://www.rfc-editor.org/info/rfc9457/) can encode structured
  cancellation errors, but does not define cancellation lifecycle semantics.
- [IETF HTTPAPI WG documents](https://datatracker.ietf.org/wg/httpapi/documents/)
  do not currently show an active generic operation-cancellation draft.

## Measurement Caveats

- Current discovery uses metadata and GitHub Search terms, so many selected
  repositories are workflow-adjacent but not HTTP API implementations.
- Prevalence claims are conditioned on this workflow/job/task-biased corpus.
  They should not be presented as a population estimate for all HTTP APIs.
- Current extraction remains conservative for dynamic route registration.
- OpenAPI and Swagger files can still be duplicated inside one repository,
  especially generated version catalogs; normalized evidence now records merged
  duplicate counts.
- Evidence record counts should not drive RFC decisions directly; independent
  family counts, capped evidence counts, strict scores, and manual samples are
  safer.
- The weakest cancellation bucket is `delete-operation-resource`; it should be
  treated as supporting evidence only unless the operation path, name, or
  summary uses cancellation wording.

## Recommended Next Improvements

1. Sample 30–50 examples from each top cancellation pattern and record TP/FP
   rates before relying on the 407-family strict count in an Internet-Draft.
2. Generate a cancellation-first Internet-Draft skeleton and map each section to
   sampled corpus evidence.
3. Split broad async into narrower concepts: operation resource, operation
   status, operation result, cancellation, retry, and progress reporting.
4. Improve discovery yield by verifying server framework files before admitting
   a repository to the final seed.
5. Add more framework-specific extractors for FastAPI, NestJS, Rails route
   scopes, Spring functional routes, ASP.NET controller attributes, Laravel
   resource controllers, and Phoenix pipelines.

## Bottom Line

`http-cancellation` is the better first RFC candidate because the corpus already
shows strong convergence on a cancel affordance, especially
`POST /.../{id}/cancel`, while prior art leaves reusable HTTP cancellation
semantics split across OData, Google-style operations, Azure-style LROs, RFC
7240, and RFC 9457.

`http-async-operation` should remain the larger umbrella study. It is strong
enough to justify continued mining, but it needs stricter concept splitting
before being pitched as a precise RFC by itself.
