# 2026-09-04 5,000 Repository Result Analysis

## Executive Summary

The 5,000-repository run produced two plausible RFC candidates:

1. `http-cancellation`
2. `http-async-operation`

Both scored 68 in the current deterministic scoring model, but they are not
equally strong in the same way. Cancellation is the cleaner RFC-shaped protocol
gap. Async operation is broader and more prevalent, but the raw evidence is more
affected by generated OpenAPI catalogs and generic `job` / `task` / `run`
resource names.

## Corpus Health

- Repositories processed: 5,000
- Independent implementation families: 4,994
- Repositories with detected evidence: 660
- Repositories with no detected evidence: 4,340
- Raw evidence records: 24,647
- Extraction errors: 0

The run was operationally healthy: the pipeline completed, resumed safely during
development, and produced no final extraction errors. The main measurement
caveat is corpus yield: only 13.2% of the discovered repositories contained
routes that the current extractors could classify.

## Candidate 1: HTTP Cancellation

### Why It Is Strong

- Explicit cancellation actions appear in 390 independent families after
  excluding the weakest `DELETE job/task resource` heuristic.
- The dominant shape is `POST /.../{id}/cancel`, but the corpus also shows
  `PUT /.../stop`, `PATCH /.../terminate`, `GET /.../cancel` signed/action
  links, and `DELETE /cancel` variants.
- The concept has lower evidence concentration than async operations: the top
  repository contributes 7.48% of cancellation evidence.
- It overlaps strongly with async operation families: 89.6% of cancellation
  families also have async-operation evidence.

### Measured Shapes

| Pattern | Families |
| --- | ---: |
| `post-subresource-cancel` | 324 |
| `post-action-cancel` | 104 |
| `put-action-cancel` | 27 |
| `get-cancel-link` | 18 |
| `delete-action-cancel` | 7 |
| `patch-state-cancelled` | 5 |

### RFC-Shaped Core

The strongest proposal is not “standardize every cancel endpoint”. It is a
small HTTP interaction profile for cancelling long-running operations:

- how an operation advertises cancelability;
- how a client requests cancellation;
- what response status means “accepted, not complete”;
- what response status means “already completed, cannot cancel”;
- how clients observe terminal states after cancellation;
- how cancellation interacts with idempotency and retries.

## Candidate 2: HTTP Async Operation

### Why It Is Still Interesting

- The full detector found async-operation evidence in 607 independent families.
- A stricter subset using `202 Accepted` or explicit status resources still
  covers 308 independent families.
- A long-running-operation core of `POST job/run`, `POST 202`, and `GET status`
  covers 550 independent families.
- Observed interaction patterns include `POST 202`, `POST job/run`,
  `GET status/progress/result`, and non-POST mutations returning `202`.

### Why It Needs More Filtering

- Raw async evidence is highly concentrated: two repositories contribute about
  40% of all async evidence.
- Generated Kubernetes/OpenAPI catalogs produce repeated routes across multiple
  versioned specs.
- Generic `GET /jobs`, `GET /tasks`, and `POST /tasks` can describe ordinary
  resources rather than long-running operations.

### RFC-Shaped Core

The useful RFC target is a narrow operation-resource profile, not a broad
definition of asynchronous HTTP:

- creation request returns `202 Accepted` or a typed operation representation;
- operation resource has stable `status`, `progress`, `result`, and `error`
  fields;
- response links identify status, result, cancellation, and retry affordances;
- terminal states are explicit and reusable across APIs;
- idempotent retries are specified for operation creation.

## Measurement Caveats

- Current discovery uses metadata and GitHub Search terms, so many selected
  repositories are workflow-adjacent but not HTTP API implementations.
- Current extraction is deterministic and conservative for dynamic route
  registration, so it misses framework-specific patterns.
- OpenAPI and Swagger files can be duplicated inside one repository, especially
  generated version catalogs.
- Evidence record counts should not drive RFC decisions directly; independent
  family counts, capped evidence counts, and manual samples are safer.
- The weakest cancellation bucket is `delete-operation-resource`; it should be
  treated as supporting evidence only unless the operation name or summary uses
  cancellation wording.

## Recommended Next Improvements

1. Add per-repository de-duplication by concept, method, normalized path, and
   source kind before evidence counts are reported.
2. Add an explicit “strict mode” score using only `202 Accepted`, status/result
   resources, and cancellation verbs in path or operation names.
3. Split broad async into narrower concepts: operation resource, operation
   status, operation result, cancellation, retry, and progress reporting.
4. Improve discovery yield by verifying server framework files before admitting
   a repository to the final seed.
5. Add framework-specific extractors for FastAPI, Spring, Gin/Chi, Express,
   NestJS, Rails, Laravel, Phoenix, and ASP.NET minimal APIs.
6. Sample 30–50 examples from each top pattern and record TP/FP rates before
   converting the candidates into an Internet-Draft outline.

## Bottom Line

`http-cancellation` is the better first RFC candidate because it is narrower,
less covered by existing seeded standards, less dominated by generated catalogs,
and naturally composes with async operation resources.

`http-async-operation` should remain the larger umbrella study. It is strong
enough to justify continued mining, but it needs stricter concept splitting
before being pitched as a precise RFC by itself.
