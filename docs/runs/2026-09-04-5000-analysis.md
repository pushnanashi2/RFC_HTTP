# 2026-09-04 5,000 Repository Result Analysis

## Executive Summary

The refined 5,000-repository run still leaves two plausible RFC candidates:

1. `http-cancellation`
2. `http-async-operation`

`http-cancellation` remains the better first candidate, but the argument is now
narrower than the first report claimed. Repository/family-level async overlap
was too coarse because a repository can expose `/jobs/{id}/status` and also
`/subscriptions/{id}/cancel`; those are not necessarily the same operation
resource.

The corrected measurement therefore adds route-level operation linkage:

- strict cancellation families: 407
- strict cancellation families with same-resource async evidence: 194
- strict cancellation families targeting operation-like nouns: 222
- strict cancellation families with domain-transition risk: 297
- same-resource linked `delete-operation-resource` families: 185
- overlap between strict-linked and delete-linked families: 97
- union of strict-linked and delete-linked families: 282

These buckets are not mutually exclusive. A family can contain both true
operation cancellation and unrelated business cancellation routes. The next
external-facing claim should be: the corpus contains a large deployed
`POST /.../{id}/cancel` practice, but a manual operation-vs-domain labeling pass
is required before asserting prevalence in an Internet-Draft.

The internal score model still ranks cancellation slightly above async operation
(`69` vs `68`), but that score is now treated as triage only. External material
should lead with qualitative evidence: observed convergence, existing semantic
inconsistency, and prior-art fragmentation.

## Candidate 1: HTTP Cancellation

### Why It Is Still Strong

- Explicit cancellation actions appear in 407 independent families after
  excluding the weakest `DELETE job/task resource` heuristic.
- `POST /.../{id}/cancel` is still the dominant strict shape with 330
  pattern-family memberships.
- The standardization gap is semantic, not purely syntactic: best-effort
  behavior, terminal state, too-late-to-cancel behavior, retention, and retries
  vary across prior art.
- The concept has low evidence concentration: the top repository contributes
  3.56% of deduplicated cancellation evidence.

### Route-Level Precision Correction

The first analysis used cancellation-vs-async overlap at repository/family
scope. That inflated the motivation because unrelated routes can coexist in the
same repository. The corrected pass links a cancellation route to an async
operation only when the cancel target resolves to the same normalized operation
resource as a status/progress/result/operation route in the same repository.

It also marks a weaker `operation target` when the cancellation route targets an
operation-like noun such as job, task, operation, run, execution, workflow,
build, deployment, pipeline, export, import, backup, restore, sync, scan,
render, transcode, training, migration, index, provision, snapshot, report, or
query.

| Claim | Numerator | Denominator | Share | Safe use |
| --- | ---: | ---: | ---: | --- |
| Same-resource linkage within strict cancellation | 194 | 407 strict cancellation families | 47.7% | Operation-cancellation precision check |
| Operation-like target within strict cancellation | 222 | 407 strict cancellation families | 54.5% | Broader operation-cancellation recall check |
| Same-resource cancellation among async families | 194 | 631 async-operation families | 30.7% | Conservative async-affordance claim |
| Operation-like cancellation among async families | 222 | 631 async-operation families | 35.2% | Broad async-affordance claim after review |
| Domain-transition-risk review queue | 297 | 407 strict cancellation families | 73.0% | Precision risk requiring manual labels |

Domain-transition-risk families are a review queue, not automatic false
positives. This is the most important caution number for external readers.

The earlier “async family cancellation affordance” number of roughly two-thirds
is therefore too broad for external use. It remains useful as a discovery hint,
but the route-level numbers are the defensible denominator.

The operation-resource-centered envelope is narrower than the naive
`194 + 185` sum because the two sets overlap:

| Component | Families | Async-operation denominator | Share |
| --- | ---: | ---: | ---: |
| Strict explicit-cancel routes with same-resource async linkage | 194 | 631 | 30.7% |
| `delete-operation-resource` routes with same-resource async linkage | 185 | 631 | 29.3% |
| Overlap between those linked sets | 97 | 631 | 15.4% |
| Union of strict-linked and delete-linked sets | 282 | 631 | 44.7% |

So the current structural claim is an operation-resource-linked envelope of
194/631 to 282/631 async families. This is not yet a TP rate; manual labels
still decide how much of the envelope is true operation cancellation.

sampling stratum, not discarded evidence.

### Manual Label Criteria

Before using these counts in an Internet-Draft, sample the top cancellation
patterns and label route records with automated linkage fields hidden:

- `operation-cancellation`: the canceled target is an observable operation,
  job, task, run, execution, workflow, build, deployment, pipeline, export,
  import, backup, restore, sync, scan, render, transcode, training, migration,
  index, provision, snapshot, report, query, or status monitor.
- `domain-state-transition`: the target is a business object such as a
  subscription, order, booking, plan, invoice, reservation, or request. This
  must be judged from operation summaries, response schemas, lifecycle fields,
  repository docs, and creation responses, not from the automated
  same-resource-linkage rule.
- `ambiguous`: the route name suggests cancellation but the evidence does not
  show whether the target is an operation or a business object.

The sampling report should stratify by pattern, especially
`post-subresource-cancel`, because it is both the strongest shape-convergence
signal and the largest false-positive risk. It should also stratify by
repository/family so a large catalog cannot dominate a pattern sample. The
current representative-row sheet satisfies that requirement within each pattern:
one family can contribute at most one row per pattern before repository caps are
applied.

### RFC-Shaped Core

The strongest proposal is not “standardize every cancel endpoint”. It is a
small HTTP interaction profile for cancelling long-running operations:

- how an operation advertises cancelability;
- how a client requests cancellation;
- what response status means “accepted, not complete”;
- what response status means “already completed or too late”;
- how clients observe terminal states after cancellation;
- how cancellation interacts with idempotency and retries;
- what best-effort cancellation does and does not imply;
- who is authorized to cancel an operation, including another principal's
  operation;
- whether cancellation propagates to child operations;
- how long canceled operation state remains observable.

The interoperability beneficiary is a generic or autonomous client, not a human
reader of one API's documentation. Such a client needs a reusable way to
discover that an operation it started can still be stopped, request the stop,
and observe the terminal state without hard-coded service knowledge.

## Candidate 2: HTTP Async Operation

### Why It Is Still Interesting

- The full detector found async-operation evidence in 631 independent families.
- The strict subset using `202 Accepted` mutations or explicit status resources
  still covers 239 independent families.
- Observed interaction patterns include `POST 202`, `POST job/run`,
  `GET status/progress/result`, generic operation resources, and non-POST
  mutations returning `202`.

### Why It Needs More Filtering

- Strict evidence covers 37.9% of async families, so broad `job` / `task` /
  `run` route naming still drives much of the base score.
- Deduplicated async evidence is still more concentrated than cancellation: the
  top repository contributes 16.74% of async evidence.
- Generated Kubernetes/OpenAPI catalogs still appear in the top contributors,
  even after repository-level deduplication.
- Generic `GET /jobs`, `GET /tasks`, and `POST /tasks` can describe ordinary
  resources rather than long-running operations.

### RFC-Shaped Core

The useful RFC target is a narrow operation-resource profile, not a broad
definition of asynchronous HTTP:

- creation request returns `202 Accepted` or a typed operation representation;
- operation resource has stable `status`, `progress`, `result`, and `error`
  fields;
- response links identify status, result, cancellation, and retry affordances;
- terminal states are explicit and reusable across APIs;
- idempotent retries are specified for operation creation.

## Prior Art and Standards Gap

The prior-art comparison is maintained in
`docs/prior-art/http-cancellation.md`.

Key takeaways from the 2026-09-04 check:

- [HTTP/2 RST_STREAM](https://www.rfc-editor.org/rfc/rfc9113.html#name-rst_stream)
  and [HTTP/3 request cancellation and rejection](https://www.rfc-editor.org/rfc/rfc9114.html#name-request-cancellation-and-rej)
  cancel or abort message streams, not durable server-side operations that
  outlive the request.
- [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html) defines `202
  Accepted` and `Retry-After`, but does not define cancellation lifecycle
  semantics.
- [RFC 7240](https://www.rfc-editor.org/info/rfc7240/) defines `Prefer:
  respond-async` and gives a `202 Accepted` async response example, but leaves
  the later result process implementation-specific.
- [OData v4.0](https://docs.oasis-open.org/odata/odata/v4.0/os/part1-protocol/odata-v4.0-os-part1-protocol.html#_Toc372793755)
  defines status monitors and `DELETE` cancellation, including `202` for
  asynchronous cancellation.
- [Google long-running operations](https://github.com/googleapis/googleapis/blob/64aa30b277168edd20efee0c9ceb4ca01248931d/google/longrunning/operations.proto#L88-L105)
  define best-effort cancellation and later observation through the operation
  resource, with successful cancellation represented as a terminal error state.
- [Azure guidance](https://github.com/microsoft/api-guidelines/blob/a7022a299442a8352431874e63ec4dff548a1b81/azure/Guidelines.md#long-running-operations--jobs)
  is strong on operation-location, polling, retry guidance, and repeatability,
  while public cancellation semantics vary by guideline or service.
- [RFC 8288](https://www.rfc-editor.org/info/rfc8288/) and the IANA Link
  Relation registry are likely the smallest standards hook for advertising a
  cancellation affordance.
- [RFC 9652 Link-Template](https://www.rfc-editor.org/rfc/rfc9652.html)
  provides a published HTTPAPI WG hook for advertising templated affordance URIs
  such as `/jobs/{id}/cancel`.
- [RFC 9264 Linkset](https://www.rfc-editor.org/rfc/rfc9264.html) is a possible
  way to publish grouped operation affordances outside a single representation.
- [Idempotency-Key](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/)
  and [Link Hints](https://datatracker.ietf.org/doc/draft-ietf-httpapi-link-hint/)
  are useful HTTPAPI prior-art references. Datatracker lists both as expired
  Internet-Drafts while still recording HTTPAPI WG Document state, so cite them
  as expired WG documents rather than abandoned work.
- [RFC 9457](https://www.rfc-editor.org/info/rfc9457/) can encode structured
  cancellation errors, but does not define cancellation lifecycle semantics.
- [Events Query](https://datatracker.ietf.org/doc/draft-gupta-httpapi-events-query/)
  is relevant to terminal-state observation without polling.
- [IETF HTTPAPI WG documents](https://datatracker.ietf.org/wg/httpapi/documents/)
  do not currently show an active generic operation-cancellation draft.

## Measurement Caveats

- Current discovery uses metadata and GitHub Search terms, so many selected
  repositories are workflow-adjacent but not HTTP API implementations.
- Prevalence claims are conditioned on this workflow/job/task-biased corpus.
  They should not be presented as a population estimate for all HTTP APIs.
- The `4,993` independent-family count is still close to repository count. It
  does not prove strong implementation independence; route-set similarity and
  generator fingerprints should be added before publication.
- Current extraction remains conservative for dynamic route registration.
- OpenAPI and Swagger files can still be duplicated inside one repository,
  especially generated version catalogs; normalized evidence now records merged
  duplicate counts.
- Evidence record counts should not drive RFC decisions directly. Use
  independent-family counts, capped evidence counts, strict subsets,
  route-level linkage, and manual samples.

1. Label `docs/validation/http-cancellation-sample-2026-09-04.csv` and publish
   per-pattern TP rates plus a strict pattern-family weighted estimate with
   ambiguity bounds and sampling-error intervals only where applicable.
2. Add route-set similarity and generator fingerprint clustering before making
   independence claims externally.
3. Label `docs/validation/http-cancellation-family-sample-2026-09-04.csv`
   before updating any 407-family denominator claims in the draft motivation.
4. Split broad async into narrower concepts: operation resource, operation
   status, operation result, cancellation, retry, and progress reporting.
5. Improve discovery yield by verifying server framework files before admitting
   a repository to the final seed.
6. Add more framework-specific extractors for FastAPI, NestJS, Rails route
   scopes, Spring functional routes, ASP.NET controller attributes, Laravel
   resource controllers, and Phoenix pipelines.

## Bottom Line

`http-cancellation` remains the better first RFC candidate, but only as a
carefully scoped operation-cancellation profile. The corrected measurement shows
that route-shape convergence is real, while the precision risk is also real.

The next cut should be a labeled sampling report, not a public Internet-Draft.
Once the sample separates operation cancellation from business cancellation, the
draft can argue from a defensible subset and frame cancellation as either a
standalone profile or a section in a broader operation-resource document.
